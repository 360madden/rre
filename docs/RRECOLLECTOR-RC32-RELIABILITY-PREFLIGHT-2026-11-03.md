## Finding A — Detail batch bypasses accepted-ID cap (P2 latent)

- `abilities.lua:6,18-49` bounds the accepted list at 1,024 enumerated raw entries and 512 distinct normalized IDs, and records `truncated`/ `enumerationComplete` diagnostics.
- `abilities.lua:57-61` nevertheless calls `newApi.Detail(rawList)` using the **unfiltered original List table** rather than its capped/validated IDs. A malformed or oversized `rawList` can therefore reach the batch API even though only 512 IDs may be copied into the result. The 69/69 saved capture is below these limits and does not demonstrate an actual oversize fault.
- Correct only after checking the batch contract. If its table shape cannot be proven for a sanitized subset, **skip batch unless `enumeration.enumerationComplete == true and enumeration.duplicates == 0`** and use the existing per-ID fallback on at most 512 normalized IDs. For complete lists keep the known-good batch call. This preserves existing successful API behavior while disallowing an oversized/ignored/duplicate raw list from reaching batch. When `ignored` or `duplicates` are present, skip batch; the proposed guard already covers both conditions. This does not fully bound enumeration of an untrusted Lua table by `pairs`, but it bounds calls sent to Detail.
- Regression fixture: mock `Inspect.Ability.New.List` with 513+, 1,025+, mixed numeric/keyed, invalid and duplicate ID entries; spy on batch and scalar Detail calls; verify no uncapped `rawList` is ever sent to batch, no more than 512 scalar fallback IDs, distinct `captureComplete=false` for incomplete enumeration, previous complete capture preserved by `main.lua:156-187`, normal 69 known IDs unchanged.

## Finding B — Explicit-error candidate attempt can overwrite good prior results (P1 conditional)

- `candidates.lua:93-123` increments `counts.errors` when `newApi.Detail` raises, but `candidates.lua:170-172` returns `report` with `apiReady=true` from line 68 even when every Detail call errors.
- `main.lua:97-123` accepts any table with `apiReady=true`; it writes `RRECollectorData.candidateLookup` and increments `candidateSequence` without qualifying all-error or incomplete response health. Thus a transient endpoint failure could replace the formerly successful saved candidate result with an all-error snapshot. The existing `recordCapture` path at `main.lua:156-187` explicitly protects a prior complete catalog and is a good local pattern.
- Future guard: **if a useful prior candidateLookup exists, preserve it and its candidateSequence whenever the new report contains explicit Detail exceptions (`counts.errors > 0`)**; write a bounded `candidateAttempt` that distinguishes all-error from partial-error instead of claiming a successful replacement. If no prior useful report exists, retain or record partial responses with an explicit incomplete/error status under a documented policy. Do not reject error-free negative `nil`/no-detail outcomes; they are not exceptions and cannot establish lock or unlearnability. The more limited all-error case (`counts.queried > 0 and counts.errors == counts.queried`) is sufficient to demonstrate the existing bug but not a complete preservation guard.
- Regression fixture: source-extracted `runCandidateLookup` mock with prior good snapshot; both all-error and partial-error reports must retain the prior object and sequence with accurate attempt diagnostics; error-free all-nil/no-detail is a valid negative API result, not transport failure; normal 96-candidate positive receipt remains unchanged. A no-prior partial report must be explicitly classified. Verify no private player or unit values copied into test report.
