## Exact bounds and observable behavior

- The probe does **nothing unless an operator manually copies its text into a working LuaPad editor and clicks Run**. No file under the RIFT `Interface/AddOns` tree is changed by staging these three RRE files.
- It checks required APIs and a valid initial frame-clock reading before attaching one `Event.System.Update.Begin` listener, then monitors frame-clock progress during updates. A repeat Run supersedes the prior listener **only after confirmed detachment** through a unique temporary global slot. If an earlier Detach was unconfirmed, a sticky session-only quarantine flag prevents any further Attach until the operator reloads the UI. A blocked Run caused by a missing required API or an invalid initial frame-clock does not replace the listener or discard an already completed result.
- It waits **0.6 seconds** to avoid sampling the editor button, then watches at most **12 seconds of advancing frame-clock time** with an independent guard for **900 consecutive callbacks during which the frame clock does not advance**. A frame-clock reading that moves backward during update sampling or the final completion-time read (including a deadline-triggering update) now terminates with `CLOCK_UNAVAILABLE`, without accepting or caching a candidate; equal timestamps are not regressions and retain the 900-callback stall guard. High FPS by itself no longer shortens the 12-second window; an actual stable candidate or API error still ends it sooner. **Important:** there is no independent wall-clock watchdog: if game update callbacks stop, neither guard runs. When frames resume, the time gate can expire, or an operator can cancel/re-arm; do not assume expiry during a frozen client.
- Accepts a candidate **only** if `Inspect.Tooltip` returns `type == "ability"` and a string matching precisely `A` followed by **16 hexadecimal characters**, **identical across three consecutive frames**. Print result prefix: `ABILITY_ID_CANDIDATE_UNVERIFIED_SOURCE` with only that uppercase ability-shaped ID.
- An expired 12-second frame-clock window now reports one of three **coarse, privacy-safe sample observations** with `id=UNKNOWN`: `TIMEOUT_NO_ABILITY_TOOLTIP` means no *successful post-settle* `Inspect.Tooltip()` sample returned type `ability` (including when no eligible tooltip reads occurred); `TIMEOUT_ABILITY_NO_ID_SHAPE` means the `ability` type appeared but no value matched exact `A` + 16 hex characters; `TIMEOUT_ID_SHAPE_NOT_STABLE` means at least one matching scalar appeared but never for three consecutive identical samples. They do **not** prove what the native Soul Tree exposes or identify a Legendary variant. `TIMEOUT_NO_VALID_ID` remains accepted by old cached receipts but is no longer emitted on a new normal deadline. Other `UNKNOWN` results include `TOOLTIP_API_FAILURE`, `CLOCK_UNAVAILABLE`, and missing-API/registration failures. Never print raw `shown` variants, arbitrary objects, unit/buff IDs, source pointer values or later tooltip results.
- Detaches by exact registered callback on success, timeout, cancellation and error (avoids one-match wildcard ambiguity if another handler shares a label). If detachment fails (API exception or explicit `false`), the handler is marked inert, the result says `DETACH_UNCONFIRMED`, and a session-local quarantine flag refuses any later probe Run with `BLOCKED_UNCONFIRMED_DETACH; reload UI before another Run`. Do **not** manually clear the flag; use an operator-controlled normal `/reloadui` only after preserving evidence. The existing failure receipt survives that blocked Run. A `nil` Detach return remains a success under the established API pattern. No game cast, movement, role change, UI click/macro automation, disk write, SavedVariables serialization or network action exists in the probe.
- **The returned ID is not automatically a Protector's Fury ID or a Legendary variant.** It can be misattributed if another ability tooltip was hovered; screenshot-level correlation with the native tooltip and current role is still required.
- On completion the probe may retain **one sanitized session-memory result**: allowlisted status, optional validated A+16-hex ID, finite start/finish frame clocks and detachment outcome—never raw tooltip/unit data. Only a new probe that passes API and initial frame-clock checks and reaches the attach attempt clears a prior result; missing-API, invalid-initial-clock and failed-detach-quarantine blocked Runs preserve any completed receipt. The separate copy helper prints and consumes the result only when an operator runs it with a valid frame-clock reading; when the clock API fails or returns a nonfinite value and a cached record exists, it prints `BLOCKED_CLOCK_RETRY` and preserves the record for another operator-run attempt. The helper does not inspect the tooltip or modify game state. Initial API/clock blockage with no prior receipt, or an unavailable, nonfinite or regressing completion clock on a completed probe, can leave no retrievable record. In that case an operator sees `CLOCK_UNAVAILABLE id=UNKNOWN` in RIFT chat, not a copied ID.
