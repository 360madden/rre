## What the combined evidence proves

1. **Conditional root key writer, not a confirmed player ID.** In wrapper `0x7F2570`, the incoming object reference enters helper `0x1EBECF0`; the wrapper copies `QWORD[returned_reference+0x18]` to RDX, obtains the `0x49A020` root singleton as RCX, and calls `0x580580`. The setter compares the candidate against `QWORD[root+0x360]` at `0x5805CE`, conditionally resets **root+0x358** at `0x580653`, and stores the key at `0x580693`. None of this proves the branch executed in the current game.
2. **An actual registry-key consumer.** `0x6A0040` passes 64-bit `root+0x360` to `0x58C990`, which compares keys at hash-chain node+0x08. It saves a returned container pointer at **root+0x3F8**; a downstream selection caches a *different* component at **root+0x400**. The source therefore qualifies `root+0x360` as a **lookup key**. A key may be opaque; there is **no established equality** with Lua `player.id`, an actor pointer, target ID, or that cached component.
3. **Shared dynamic type discriminator.** ROOT helper `0x1EBECF0–0x1EBED55` (SHA `0c6045c0fe2fe250595ba98f75a6fb452d2d21e847941d36ea6f4ef45b271f29`) copies/retains a reference, invokes `0x127303C`, compares the returned AX to `0xDD3C`, and can decrement/clear the reference. Previously verified [SC-604 indirect discriminator](REA-RIFT-SPELLCASTING-SC604-INDIRECT-DISCRIMINATOR-2026-11-07.md) proves `0x127303C–0x1273057` first calls `[input_vtable+0x40]`, then tail-jumps through `[returned_vtable+0x08]`. Related callers compare AX with `0x0139`, `0x0131`, or `0x0E89`. These are **caller comparison values, not proven object/class IDs**. The *indirect target implementations and return meanings* remain unknown.
4. **New data-referenced wrapper record.** Independent bounded original `.text` scan found **zero direct E8 calls or RIP-relative LEA references** to wrapper RVA `0x7F2570`, but one initialized 64-bit pointer to its image VA `0x1407F2570` at file offset `0x2F5BC20` / **RVA `0x2F5D620`**. Its 24-byte `.data` triple is:
   - RVA `0x2F5D618` → VA `0x1435159F8` (global **RVA `0x35159F8`**)
   - RVA `0x2F5D620` → VA `0x1407F2570` (ROOT wrapper)
   - RVA `0x2F5D628` → `0`
   The record **suggests** registration/callback metadata, but this is an **inference**, not proof of a runtime invocation or which object owns the upstream producer.
5. **Three independently decoded global-reference paths.** At `0x34C965`, code loads a constant `0x4EEF798E`, the address of global `0x35159F8`, and jumps to `0x126EA44`. At `0x1EC50C3`, a conditional lookup/initialization path passes that address to `0x127663C`; its alternate path visits `0x1ECE1C0` and `0x1276A6C`. At `0x1ED56C0`, a key-range-selection function returns the global address for one bounded key interval. Exact source context hashes: `0x34C950+0x70` = `a7b43e5b93c96ae88cba1cf06052e504a4a0668a539f5fa47f35fd904a5e9f82`; `0x1EC50A0+0x90` = `f1f38f0829258fc80956676bac1e4af164a0c813593ee0c34dbe837712b06d75`; `0x1ED56A0+0x90` = `fd89c5d71a8a1c6b43a0df9ef0282de11fcd1bdee94f361759456d659f75515a`.

## Decision / narrow next steps

**Accepted:** static registry-key role; conditional setter path; side-effecting helper; shared two-stage indirect dispatch; existence of a data-referenced wrapper record and three global-reference paths. **Not accepted:** root key equals `player.id`; type tag `0xDD3C` names a player class; proven callback ABI or live dispatcher; nonzero write; present physical process identity; permission to invoke native helpers.

1. **RRE source-only next trace:** inspect `0x126EA44` registration-like path, then `0x127663C`/`0x1276A6C` and `0x1ECE1C0` in separate bounded original-byte probes. Park if two probes cannot connect the descriptor to an actual producer/instance.
2. **RR2 owner only:** with a newly authorized same-PID/start/build physical observation, reuse existing read-only `CurrentBuildPlayerLookup`, compare `root+0x360` against independently sourced current Lua `player.id` in one epoch, and separately log `player.target`. Fail closed on null, stale, mixed epoch, or inconsistent byte identity. Do not add a new reader or invoke side-effecting RRE functions.
3. **Live acceptance gate:** independently verify loaded source and actually observed state transitions before promoting the key to a player locator. Do not reinterpret prior VM, historical screenshot, or saved-variable records as proof of this physical session.
