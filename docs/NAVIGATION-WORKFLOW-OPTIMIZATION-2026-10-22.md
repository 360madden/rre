## Working-method and test-budget changes

- **One blocker at a time.** Manager owns the task board/critical path; RR2 retains exclusive control/capture ownership. Assign an additional AI reviewer only for a genuinely independent, measurable evidence question and only after confirming a real model session exists. Workbridge command slots are not AI agents.
- **No tool before a reproducer.** If a capability is missing, identify the exact failed existing operation and owner before writing software. Prefer `read_files`, `task_context`, narrow `search_text`, `command_list`, Workbridge's existing patch/config/workflow tools, and already installed RR2 image/Python helpers. Do not create NAV-007 as another generic adapter.
- **No pointless validation loops.** During code changes run the smallest focused test immediately; perform one complete RRE gate per cohesive source integration, not a full ~500-test gate after each report or doc. For docs/board-only updates run `node tools/validate-roadmap.mjs`, check links/current file hashes and review the diff. A source change invalidates the earlier gate; rerun only when warranted.
- **Bound work.** Each probe specifies the question, saved inputs, owner, limit, alternate hypothesis and what observation changes the decision. After **two distinct non-decisive probes**, park it unless a new source or behavior is available. A tool safety block ends that route immediately; do not bypass.
- **Measure real progress.** Report (a) P0–P4 gate states, (b) actual game actions and observations, (c) remaining uncertainty and reason, (d) test exits and integration commits when code changes. Do not lead with a growing test count or claim offline success means autonomous navigation.
- **Limit context and repository churn.** One short active handoff; source excerpts instead of 140 KiB task-board dumps; one atomic file-set patch where feasible; no modifying another workflow's dirty RR2 checkout. Don't spawn agents or retry long whole-binary imports as a placeholder for blocked game evidence.
- **Separate active status from historical evidence.** Queue/grant, VM PID, game process, receiver instance, foreground, screenshot, gesture, input receipt and telemetry can expire independently. A successful lease/capture only proves its specific boundary.
